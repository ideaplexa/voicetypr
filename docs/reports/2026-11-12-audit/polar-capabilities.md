# Polar capability research

Documentation accessed 2026-11-13. Polar documentation is live and may describe newer features; version `2027-01` is explicitly future-versioned and should not be assumed available today.

## 1. Licence keys — **Yes**, direct public client calls

- Production base `https://api.polar.sh`. Public, unauthenticated: `POST /v1/customer-portal/license-keys/activate` requires `key`, `organization_id`, `label`, optional `conditions`, `meta`; response activation `id` must be persisted. `POST /v1/customer-portal/license-keys/validate` requires `key`, `organization_id`; `activation_id` is required when activation limits enabled; optional `conditions`, `benefit_id`, `customer_id`, `increment_usage` (nonnegative integer). `POST /v1/customer-portal/license-keys/deactivate` requires `key`, `organization_id`, `activation_id`; success 204. The similarly named `/v1/license-keys/*` core endpoints require privileged authentication; never embed an organization token. [activate](https://polar.sh/docs/api-reference/2026-10/customer_portal/activate-license-key), [validate](https://polar.sh/docs/api-reference/2026-10/customer_portal/validate-license-key), [deactivate](https://polar.sh/docs/api-reference/2026-10/customer_portal/deactivate-license-key), [API auth](https://polar.sh/docs/api-reference/2026-10/introduction).
- A benefit may set `limit_activations` and `limit_usage`; `increment_usage` increments quota at validation. Activation limit reached/revoked/expired gives 403; validation of revoked, disabled, expired, wrong activation/conditions/benefit/customer gives 404; excess usage increment gives 400. Successful validation returns `status` (constant `granted`), `customer_id`, `customer`, `benefit_id`, `expires_at`, `activation` (nullable, containing `id`, `label`, `meta`), `usage`, `limit_usage`, `limit_activations`, and other fields. Check `benefit_id` to scope access to the correct product benefit. [feature](https://polar.sh/docs/features/benefits/license-keys), [validate schema](https://polar.sh/docs/api-reference/2026-10/customer_portal/validate-license-key), [activate schema](https://polar.sh/docs/api-reference/2026-10/customer_portal/activate-license-key).
- **Partly device binding:** put a device-hash string in `conditions` at activation, send the exact same object with validation; Polar checks equality. `meta` is stored/displayed information, not a matching condition. Both allow up to 50 primitive fields, names ≤40 chars, strings ≤500 chars. This is client-asserted, not hardware attestation; hash/activation can be copied or spoofed by a modified client [INFERENCE]. [activate](https://polar.sh/docs/api-reference/2026-10/customer_portal/activate-license-key), [feature](https://polar.sh/docs/features/benefits/license-keys).
- Rate limits: unauthenticated key endpoints 3 requests/second in both environments; general production 500/minute and sandbox 100/minute per organization/customer or OAuth client, 429 with `Retry-After`; per-key-endpoint aggregation dimension **not confirmed**. [API overview](https://polar.sh/docs/api-reference/2026-10/introduction).
- **Offline: not confirmed**: documentation recommends online validation per premium-app session and does not document signed offline licences or a revocation-aware offline grace mechanism. Any local cache/grace is app policy, cannot reflect revocation while disconnected, and is tamperable [INFERENCE]. [integration](https://polar.sh/docs/features/benefits/license-keys).

## 2. One-time purchase and devices — **Yes**

A one-time product can grant a key benefit with N activation instances. Polar portal lets customers view/copy keys and deactivate activations **if enabled**, also rotate a compromised key. One-time expiry is optional and N days/months/years after purchase; subscription expiry setting is ignored and keys are revoked on subscription end. [license benefit](https://polar.sh/docs/features/benefits/license-keys).

Refund nuance: one-time order refunds default to revoking benefits, but merchant can disable revocation; subscription order refund alone does not revoke access, cancellation/revocation of the subscription is needed. Polar's proactive anti-chargeback refund cancels related subscription and revokes benefits. A revoked key fails validate. [refunds](https://polar.sh/docs/features/refunds), [license benefit](https://polar.sh/docs/features/benefits/license-keys).

## 3. Trials — **Partly**

- Native trial is for **recurring subscriptions**, configurable on product, checkout link or session; Polar says it collects payment information at checkout, charges after the trial unless canceled. Native one-time-product trial: **no documented support**. [trials](https://polar.sh/docs/features/subscriptions/trials), [products](https://polar.sh/docs/features/products).
- **Yes in principle:** a free one-time product can gate benefits behind signup, and its key benefit can expire N days/months/years after purchase. Open its checkout only when user clicks Start trial, not at sign-in. A zero-price checkout's exact email verification, card requirement, and whether expiry begins precisely at grant versus purchase: **not confirmed**; docs say one-time expiry is measured from purchase. [products](https://polar.sh/docs/features/products), [license benefit](https://polar.sh/docs/features/benefits/license-keys).
- Native subscription **Prevent trial abuse** is optional and blocks repeat trial by normalized email OR payment fingerprint across organization's products; checkout refreshes without trial, allowing full-price purchase. This is not documented to cover free one-time purchases. A one-free-product-per-customer/email constraint or unbypassable anti-repeat entitlement for that workaround: **not confirmed**. Enforce verified identity and issuance policy yourself if essential; new email/device remains an abuse vector [INFERENCE]. [trial abuse](https://polar.sh/docs/features/subscriptions/trials#preventing-trial-abuse).

## 4. Identity — **Partly**

Polar hosted customer portal signs existing purchasers in via email and one-time code; it is a portal session, not a documented callback proving customer identity to our desktop. `POST /v1/customer-sessions/` is server-side, privileged (`customer_sessions:write`), creates short-lived customer token and `customer_portal_url` for an already identified customer. [portal](https://polar.sh/docs/features/customer-portal/navigate-customers), [sessions](https://polar.sh/docs/api-reference/2026-04/customer-sessions/create-customer-session), [API auth](https://polar.sh/docs/api-reference/2026-10/introduction).

Polar also documents genuine OAuth/OIDC authorization code + `openid email`, signed `id_token`, `/v1/oauth2/userinfo`, and public-client PKCE without client secret. However this authenticates a Polar **user** and consented organization access; its equivalence to email-OTP **customer portal** identities, or automatic linkage to a merchant customer/entitlement, is **not confirmed**. Thus do not assume Polar portal is a drop-in app authentication provider; for email login independent of purchase and a managed proxy, use an app auth/session layer and explicitly reconcile identities. [OAuth](https://polar.sh/docs/integrate/oauth2/connect), [portal](https://polar.sh/docs/features/customer-portal/navigate-customers).

Customer `external_id` is organization-unique and immutable once set. Privileged customer-state API by internal or external ID returns customer, active subscriptions, granted benefits and active meter balances; `customer.state_changed` sends the state on customer/subscription/benefit changes. [customers](https://polar.sh/docs/features/customer-management), [state](https://polar.sh/docs/integrate/customer-state), [state API](https://polar.sh/docs/api-reference/customers/get-customer-state-by-external-id).

## 5. Metering and credits — **Partly**, Polar can be billing ledger, not enforcement engine

Events represent usage (e.g. speech seconds or model tokens), `POST /v1/events/ingest` carries `name`, `customer_id` or `external_customer_id`, and `metadata`; meters filter/aggregate events. Credits benefit grants units once for one-time purchase (top-up) or per subscription/meter cycle, with optional rollover. Customer state or privileged `GET /v1/customer-meters` exposes balances. With metered pricing overage can be billed; for credits-only, omit metered price. Polar explicitly never blocks usage on exhaustion. [event ingestion](https://polar.sh/docs/features/usage-based-billing/event-ingestion), [events API](https://polar.sh/docs/api-reference/events/ingest), [usage overview](https://polar.sh/docs/features/usage-based-billing/introduction), [credits](https://polar.sh/docs/features/usage-based-billing/credits), [benefit](https://polar.sh/docs/features/benefits/credits), [meters](https://polar.sh/docs/api-reference/current/customer_meters/list-customer-meters).

Own server must authenticate user and entitlement, protect upstream provider keys, price/measure real usage, check/enforce available credit and coordinate simultaneous requests/reservations so concurrency or delayed updates cannot overspend, ingest reliably and reconcile; direct customer-provided usage is untrusted [INFERENCE]. Ingested events are immutable and late events are billed in the cycle **received**, not their timestamp. The docs do not promise atomic check-and-reserve/debit; do not assume strict real-time budget enforcement from a balance read [INFERENCE]. [ingestion](https://polar.sh/docs/features/usage-based-billing/event-ingestion), [credits](https://polar.sh/docs/features/usage-based-billing/credits).

Manual credit API `POST /v1/customer-meters/credits` is documented **only for API version 2027-01** (future relative to research date), units 1–1,000,000,000, optional idempotent `external_id`, default `rollover: false`; not confirmed available today. Purchase-based top-ups and dashboard credits are documented independently. [credits](https://polar.sh/docs/features/usage-based-billing/credits).

## 6. Webhooks — **Yes**

Use `order.paid` for successful order, `order.refunded` / `refund.created` / `refund.updated` for refunds; `benefit_grant.created`, `.updated`, `.revoked` for provisioning; `customer.state_changed` for active subscriptions and granted benefits; `subscription.created`, `.active`, `.updated`, `.canceled`, `.revoked`, `.past_due`, `.cycled` for lifecycle. Cancellation can be scheduled: `subscription.canceled` alone need not mean loss of access; revocation follows end of period. `subscription.cycled` fires before renewal payment and is not proof of payment. Verify webhook signatures and make handling idempotent, treating events as notifications not authority [INFERENCE]. [events](https://polar.sh/docs/integrate/webhooks/events), [state](https://polar.sh/docs/integrate/customer-state), [webhooks](https://polar.sh/docs/integrate/webhooks).

## 7. Fees and MoR — **Yes**

Polar is reseller/MoR and handles global sales tax liability, collection and remittance; seller remains responsible for own income taxes. [MoR](https://polar.sh/docs/merchant-of-record/introduction).

Published Starter for organizations created on/after 2026-05-27 is 5% + $0.50 per transaction; on $39 and $9 US-card transactions before tax/other fees, respectively $2.45 and $0.95 (net $36.55 and $8.05). Non-US card +1.5%; tax can enter total transaction value. Earlier qualifying organizations retain Early Member 4% + $0.40 plus 0.5% for subscription payments: $1.96 on $39 and $0.805 on $9 before rounding/tax/extras. Paid tiers, payout charges, $15 disputes, and nonrefundable original transaction fees on refunds also apply. Rates depend on actual account and checkout; verify Polar account's plan. [fee schedule](https://polar.sh/docs/merchant-of-record/fees).

## 8. iOS/App Store — **Not documented**

Polar's public endpoint docs mention mobile clients, but no Polar documentation found establishing that selling iOS access outside the App Store complies with Apple's rules. Do not infer compliance; separately check applicable Apple terms and jurisdiction. [public client](https://polar.sh/docs/api-reference/2026-10/customer_portal/validate-license-key).

## 9. Limitations and issues — **Yes**

- [#14841](https://github.com/polarsource/polar/issues/14841) open: dashboard activation-limit field accepts nonnumeric text; report, not independent verification.
- [#9282](https://github.com/polarsource/polar/issues/9282) open: customer-portal meter API may omit free-plan meters; maintainer explains customer-portal scope and suggests privileged `/v1/customer-meters?customer_id=...`; product metadata intentionally stripped from portal responses. Current behavior should be rechecked before relying on it.
- [#12027](https://github.com/polarsource/polar/issues/12027) closed: concurrent activations reportedly exceeded limit; maintainer says fixed by [#12346](https://github.com/polarsource/polar/pull/12346). Historical issue, not evidence current deployment vulnerable.
- Documented subscription trial abuse protection does not establish repeat prevention for free one-time product; meter enforcement remains merchant responsibility. [trials](https://polar.sh/docs/features/subscriptions/trials), [credits](https://polar.sh/docs/features/usage-based-billing/credits).

## Smallest design that makes Polar the only licence authority

1. Configure paid one-time product and separately free one-time trial product, each with an appropriately scoped Polar licence benefit, activation limit and trial expiry. On explicit Start trial, open free-product checkout; on purchase, open paid checkout. Customer retrieves key via Polar portal. A verified app account and backend policy are still required if repeat-trial protection or account login is a hard requirement; free-checkout identity/card behavior remains unconfirmed. [products](https://polar.sh/docs/features/products), [benefits](https://polar.sh/docs/features/benefits/license-keys), [portal](https://polar.sh/docs/features/customer-portal/navigate-customers).
2. Desktop calls `POST /v1/customer-portal/license-keys/activate` with `{key, organization_id, label, conditions: {device_hash: ...}}`, stores returned activation ID; calls `POST /v1/customer-portal/license-keys/validate` with `{key, organization_id, activation_id, conditions: {device_hash: ...}, benefit_id: ...}` per session; calls `POST /v1/customer-portal/license-keys/deactivate` with `{key, organization_id, activation_id}` on device removal. Polar is sole source for licence decisions, including expiry and revocation; the app accepts only an allowed benefit. These calls require no backend or secret; offline grace is a product trade-off, not authoritative. [activate](https://polar.sh/docs/api-reference/2026-10/customer_portal/activate-license-key), [validate](https://polar.sh/docs/api-reference/2026-10/customer_portal/validate-license-key), [deactivate](https://polar.sh/docs/api-reference/2026-10/customer_portal/deactivate-license-key).
3. Own server is not necessary for basic key validation or portal access. It is necessary for a privileged customer-session API, secure account-to-Polar reconciliation and enforced one-trial issuance policy, plus future managed provider proxy, quotas and event accounting. It can query Polar and process webhooks without becoming an independent licence authority. [API auth](https://polar.sh/docs/api-reference/2026-10/introduction), [credits](https://polar.sh/docs/features/usage-based-billing/credits), [state](https://polar.sh/docs/integrate/customer-state).
